# Kernel oops excerpts: CPU 19, repro-c --mode churn-mem under load

Source: systemd journal of the previous boot (`journalctl -k -b -1`),
extracted 2026-08-18. Kernel at the time: 7.1.8-1-cachyos. The boot later
ended in a hard system crash (no further kernel log lines recorded).

## Context

- Machine: Dell Pro Max 18 Plus MB18250 (0Y3CTV), BIOS 3.3.2 (08/03/2026)
- CPU: Intel Core Ultra 9 285HX, stepping 2, microcode 0x122
- Kernel: 7.1.8-1-cachyos (tainted G O: out-of-tree nvidia modules loaded;
  see "Modules linked in" in the excerpts)
- Trigger: `repro-c --mode churn-mem` (at commit 89c2bca the mode was the
  default churn implementation; it is --mode churn-mem since 00f2e38),
  a ~500-line native C program: per round it maps a fresh 256 KiB code
  buffer, writes a small position-independent code blob, flips it RX with
  mprotect, makes fresh instance/budget pages and a fresh 4 GiB
  PROT_NONE guard-paged reservation (64 KiB committed), executes, verifies
  counters, and unmaps everything (~2500 rounds/s per run).
- Conditions: process pinned to CPU 19 (taskset); eight /usr/bin/yes
  workers pinned to P-cores 0-7 (package load). No Node, V8, wasm, or
  PGlite involved. No overclocking; laptop running a normal desktop
  session.
- The same machine reproduces userspace SIGSEGVs with si_addr equal to
  the intended address plus exactly 2^42 (bit 42 set) in V8/wasm
  workloads on the same core under the same load; see README.md
  "Platform-level fault-address investigation".

## Why these oopses matter

Oops [#1] is a kernel-mode instance of the same +2^42 signature:

- RIP `entry_SYSCALL_64_after_hwframe+0x11/0x7e` is the `push %r14`
  saving user registers on the kernel stack (see the Code line: the
  bracketed bytes `<41> 54` are that push).
- Incoming registers identify the syscall: RAX=10 (mprotect),
  RDI=0x7fd21deb5000, RSI=0x40000, RDX=5 (PROT_READ|PROT_EXEC) - the
  churn loop's W^X flip of its 256 KiB code buffer.
- RSP was `ffffd20d8b2d3f68`, so the push should have written at
  `ffffd20d8b2d3f60`. CR2 (the faulting address) was
  `ffffd60d8b2d3f60` = RSP-8 with **bit 42 set** and nothing else:
  supervisor write access to a not-present page, error_code 0x0002.
- No valid x86-64 execution of that instruction produces that address;
  the page-table walk (PGD/P4D present, PUD 0) confirms the address was
  corrupted before translation, matching the userspace captures where
  the architectural register state is clean and only the fault address
  carries the extra bit.

Oops [#2] (same RIP, same syscall shape, ~16 minutes later) aborted
syscall entry with IRQs disabled ("exited with irqs disabled",
"preempt_count 1") and left the process unkillably D-stuck in exit_mmap.
Its kernel stack, captured via sudo from /proc/1320017/stack while wedged:

    [<0>] exit_mmap+0x13e/0x320
    [<0>] __mmput+0x41/0x100
    [<0>] do_exit+0x205/0x5c0
    [<0>] make_task_dead+0x80/0x150
    [<0>] rewind_stack_and_make_dead+0x16/0x20

The wedged process survived SIGKILL for over an hour until the machine
was rebooted.

Cross-kernel note: on 7.1.8-arch1-3 (stock Arch build, same base
version), 60 loaded churn-mem runs produced no userspace fault and no
kernel oops. Against the ~2.5%/run oops rate implied by the cachyos
session, a clean 60-run batch has ~20% probability by luck alone, so
kernel-build durability is suggestive, not established. Userspace fault
rates are identical across both kernels (10/10 under the same recipe).
